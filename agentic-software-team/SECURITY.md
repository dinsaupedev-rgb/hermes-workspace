# SECURITY

Threat model: agents are LLM-driven; treat all model output and generated files as untrusted input.

## Controls in place

1. **Least-privilege tool scopes** — `POLICY_TOOL_SCOPES` maps each agent role to allowed tools; the ToolGateway throws on out-of-scope calls. PM/architect cannot touch the repo; QA cannot deploy.
2. **No model-supplied shell** — terminal execution is limited to fixed steps (`node --test`) run from our runner; the LLM supplies 0 commands. Shell execution inside generated apps is scanned and flagged.
3. **Path safety** — repo writes reject absolute paths and `..` traversal; generated apps are additionally tested for traversal blocking.
4. **Output sanitization** — `sanitizeToolArgs` caps string lengths, drops functions/undefined; parsed JSON is balanced-brace-extracted (no eval-style parsing).
5. **Secrets** — API keys read from `.env` only; `.env` gitignored; no secret enters prompts.
6. **Budget guard** — hard USD cap stops model calls; prevents runaway loops (3-attempt ceilings everywhere).
7. **Heuristic scans** — eval(), hardcoded secrets, shell usage, innerHTML are flagged; HIGH/CRITICAL → pipeline blocked.
8. **Human approval** — code changes and production deployment pause execution (UI + REST decision points).

## Prompt-injection posture

- External content only enters as part of an idea string inside a user message; artifacts generated by agents are JSON and rendered data, never re-parsed as instructions.
- Dashboard renders all model/agent text via HTML escaping.

## Known gaps (MVP)

- Dashboard artifact viewer uses `alert()` for now (no markdown rendering = no XSS surface, but UX is basic).
- No dependency audit (npm audit) wired into the security agent yet.
- No rate limiting/auth on the local API (bind only to trusted networks).
